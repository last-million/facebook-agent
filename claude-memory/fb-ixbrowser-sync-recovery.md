When a prod run posts 0 and auto-blacklists profiles in sequence, the cause is usually NOT Facebook/account suspension. On 2026-06-09 a 200-run produced 0 posts with `IXBrowser profile-open error 1004: Profile Open Failed` and false-blacklisted p75/p72. Real root causes (in order of impact):

1. **Stale 2nd posting group.** `groupAssignmentData` had TWO groups — the user's `o1498765421290862` (=id 1098414320641851) AND a stale `4854972804605257`. Profiles assigned to the stale group hit `cannot_post_in_group`. Fix: consolidate `groupAssignmentData` to ONE entry for the user's group with all unique profiles merged (preserve `requiresAdminApproval`, set `sharePercent:100`). The autopilot builds slots fresh from `groupAssignmentData` each tick, so no plan re-prep needed.
2. **ixBrowser wedge** = orphaned chrome.exe sessions ixBrowser lost track of → 1004 on new opens. Fix: `POST /api/profiles/close-all`, then kill leftover `chrome.exe` (Pinterest is `msedge.exe` — never touch). Verify with a small armed test.
3. **Bloated over-bench blacklist.** `state.ixbrowser.failedProfiles` is append-only and grew to 735+ lines, but `currentlyBlockedProfilesSummary` (GET `/api/profiles/blocked`) is the ONLY authoritative blocked list — a raw line-scan double-counts stale entries. Fix: `POST /api/ixbrowser/clear-failed-profiles` (safe: un-benches automation failures, PRESERVES genuine FB suspensions) + `POST /api/ixbrowser/reconcile-profiles {force:true}` (run twice for the 2-miss removal debounce).

Ground-truth diagnostic: compare `POST /api/integrations/ixbrowser/test` (fresh total) + `/api/integrations/ixbrowser/profiles` (live ids) vs roster ids from `groupAssignmentData`. Removals ALREADY auto-sync via the per-tick reconcile (line ~8388); only profile 2 was stale, [40,41,42,43] are reserved.

SUPPLY STARVATION (run posts a few then idles): readyCount low despite many harvested records. TWO independent re-use gates both must pass: (1) `state.posting.contentSources.reuseHours` (harvested, default 26h) checked in productHasReadyAssets (~7578); (2) `state.productDiscovery.reusePostedProductAfterDays` (default 7 DAYS) via recentlyUsedProductKeys (~2463) — this 7-day gate silently overrides the harvested reuseHours. ALSO: the 7-day image-retention sweep sets `imageDeleted=true` but the image FILE often still exists on disk → productHasReadyAssets skips it. Recovery on 2026-06-09: set reuseHours=6, imageRetentionDays=30, and atomically reconciled the jsonl (set imageDeleted=false on every record whose image file still exists) → readyCount 2→12. buffer readyCount can lag one tick after such edits (recomputes via assetBufferStatus→collectProductUrlsForPosting ~2736). Per-post-unique #fb tag (harvestedHashtags now takes a 5th `uniqueSeed` arg = trackingSeed) + bare-domain stripping in cleanHarvestedPostText (URL only in comment) were deployed via restart (backup server.js.bak_20260609_ixsync). REAL volume fix = more harvest SOURCE groups (current source o38679876833911 is exhausted); recycling 12 products toward 200 is spammy/account-risky.

HARVESTED CONTENT CONTRACT (operator-confirmed 2026-06-09, all deployed): (1) post body = EXACT harvested caption, NO length cap (cleanHarvestedPostText(text, 60000); record stores up to 60k) — only their urls/bare domains/#hashtags/see-more/CTAs stripped (url belongs in the COMMENT); (2) #tags built from the product's REAL og:title/og:description fetched from the harvested link — fetched IN the harvest browser (connector opens link in a new page of the logged-in profile, real fingerprint, no bot wall; capped 10/round, 20s, fail-soft) + server-side backfill sweep `backfillHarvestedOpenGraphAsync` per tick + manual POST /api/content-sources/og-backfill. PROVEN: plain server fetch gets bot-walled by walmrt.us/mavlynk and amzlink returns storefront junk ("Kelly's Amazon Page") — junk guard rejects storefront/bot titles, falls back to caption-derived harvestedShortTitle (which is good: sellers paste product names in captions); (3) comment = firstCommentUrl EXACT match (no lead-in phrase, never re-shortened) — harvested branch of commentText in preparePostingPlan.
