2026-06-16 — chased "posting has idle gaps / buffer stuck ~40/200 / prepares 0". After the ix-open quota (→1000/day) and parallelism (cap→5/4) bottlenecks were cleared, the BINDING constraint is now **product SUPPLY**, and it is NOT a code bug.

**THE REAL NUMBER: only ~136 UNIQUE harvested products exist.** `data/harvested-products.jsonl` had 314 LINES but **`readHarvestedProducts` (server.js ~2043) dedups by `firstCommentUrl`, LAST-occurrence-wins** (append-only log: a new merged line is appended on every post/update, so lines ≫ unique products, and the last line carries the latest `posted`/`lastPostedAt`). **GOTCHA for any future supply analysis: dedup by firstCommentUrl + use the LAST line's timestamp — do NOT count JSONL lines or first-occurrence dates** (that mistake made me think 240 were ready when the server correctly saw 31). Live: 136 unique, 12 never-posted, 73 within-48h reuse, 63 outside → minus ~30 per-run claims = **~31 ready** (matched the server exactly). Agent is in harvested-EXCLUSIVE mode (posting.contentSources.enabled+exclusive=true; web `product-candidates.jsonl` is empty).

**THROUGHPUT CEILING from this pool: ~136 ÷ (48h reuse / 24h) ≈ 68 posts/day**, ~31–63 postable at any instant. The buffer target (assetBufferTargetCount → 200) is UNREACHABLE from 136 products, so the buffer always shows a big shortfall + posting drains then waits for the 48h rotation = the idle gaps. **To post more: (1) HARVEST MORE products (grow the 136 pool — the sustainable fix), (2) shorten contentSources.reuseHours (48h→24h ≈ doubles rotation but more per-product repetition), or (3) accept ~68/day.** Operator decision pending.

**TWO CODE FIXES shipped 2026-06-16 (commit 62d8f20, deployed + pushed) — correct but they do NOT add supply:**
1. **Harvested excluded from the asset-buffer FILL loop** (fillAssetBufferAsync ~8610): harvested products cannot be "prepared" (no SYL shortlink, no review-image extraction — their image+link come from the HARVEST step; readiness is intrinsic via productHasReadyAssets). Sending their `harvested:<hash>` pseudo-URL through `generateShopYourLikesExtensionLinks` → `assertAllowedDiscoveryPageUrl` threw **"Browser discovery source URL must be HTTP or HTTPS"** (protocol `harvested:` fails the http/https check at ~6244) → linkOk:0, prepared:0, + wasted a dedicated-SYL profile-open each batch. Now the batch filter drops `harvested:` URLs → attempted:0, no crash, no wasted open.
2. **Harvested bypass the web-discovery used/no-photo registers** (assetBufferStatus ~7982): the harvested branch now runs BEFORE the `usedKeys`/`noPhotoKeys` checks, so harvested products are gated ONLY by their own 48h `contentSources.reuseHours` (in productHasReadyAssets), NOT the 7-day `productDiscovery.reusePostedProductAfterDays` (usedProductReuseWindowDays) that bleeds in via the shared used-products.txt. (NOTE: this makes harvested products repost at the operator's configured 48h instead of being held 7 days — raise contentSources.reuseHours if less repetition is wanted.)
