**WHY OPENS WERE THE BINDING CONSTRAINT** — at 100/day ÷ ~2 opens/post (publisher + commenter, approval extra) = ~17-30 posts/day. The NEW ceiling for safe volume is: **profile count / FB account safety** (only ~4 working profiles 8,10,12,19 → 100 posts = 25/profile/day = ban-risky; need MORE profiles, not more opens), product supply, and the 18:00-23:00 ET window. **SELF-LEARNING OPEN-BUDGET + AUTO-ADAPT (operator asked "can he know the plan + adapt automatically, but NO CPU/server load?"):**
- The ixBrowser LOCAL API (127.0.0.1:53200/api/v2) does **NOT** expose plan/quota — PROBED every candidate (account-info/member-info/user-info/account/plan-info/quota) → all `1007 Not Found`; no cloud apiKey configured. The agent CANNOT read the subscription directly (that's in ixBrowser's cloud dashboard behind the account login).
- So it **LEARNS** the ceiling from its own activity at near-zero load (server.js ~14688 block): counts every real open the connector already logs as step `ix_open`/`ix_open_fallback` (a CDP-reuse logs `ix_reuse` and costs NO open → NOT counted); `recordIxBrowserOpensFromObjects(objects)` hooked into `runLiveFacebookPostScript` at BOTH the success (~11316) and error (~11293) parse (mutually exclusive). When `1018` fires, opens-counted-so-far == the plan's true daily limit → `operator.ixLearnedDailyOpenLimit = max(prev, count)` (auto-updates if the plan changes; no hard-coded number).
- **AUTO-ADAPT**: `keepOpenEnabled()` now returns `operator.keepOpenSessionEnabled===true || ixOpenBudgetNearLimit()` — near 85% of the learned limit it AUTO-enables keep-open to stretch remaining opens; at the limit the existing `ixOpenCapHitUntil` pause takes over. **ENTIRELY INERT until a 1018 has ever been seen** (learnedLimit=0 → nearLimit=false → posting byte-for-byte unchanged), so on the new ~1000/day plan it's pure visibility until/unless the ceiling is approached.
- **ZERO hot-path disk I/O** (the operator's hard constraint): `readState()` reads+parses+deepMerges+normalizes the state FILE on EVERY call (no cache, server.js ~789), and `keepOpenEnabled()` runs several times per post — so the learned limit is cached in module var `__ixLearnedLimit` (hydrated once on first-touch, updated on 1018); `ixLearnedDailyOpenLimit()`/`ixOpenBudgetNearLimit()` read the module var, NOT disk. The daily count is in-memory `__ixOpensToday` (+`__ixOpensTodayDate`), persisted to `operator.ixOpensToday/Date` THROTTLED (≤1 write/2min) so it survives a restart; reset to 0 at local midnight (learned limit persists across days). Counting hook is fully try/catch (never breaks a post).
- **SURFACED** in the Prod-tab report: `buildRunReports` adds `openBudget: ixOpenBudgetSnapshot()` (opensToday / learnedLimit / remaining / pct / nearLimit / auto-or-manual keep-open); `web/report.html` renders a budget banner (id `openbudget`). New state fields persist like `ixOpenCapHitUntil` does (operator preserves dynamic fields; not in defaults, not stripped by normalizeWorkflowState).
